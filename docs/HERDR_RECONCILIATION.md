# Herdr reconciliation core (not connected to live CLI)

`scripts/herdr_reconcile.py` implements a mock-tested, fail-closed state machine. It is not a Herdr adapter and cannot bootstrap anything by itself. `scripts/bootstrap-herdr.sh` remains blocked. Do not remove the hold based on unit tests.

A future live adapter must authenticate and pin every read and mutation to the same actual Herdr server **incarnation**, not merely a socket path, server name, client-supplied token, process ID or session name. It must establish the installed CLI/API's server identity and actual workspace/tab metadata and make an atomic server identity check with every operation, or fail closed if that cannot be established. It must normalize API data to the contract in the module and produce complete, authoritative workspace and tab inventories with stable IDs, labels, and immutable server-provided creation-bound canonical cwd for workspaces and tabs. A live pane cwd can change and cannot prove workspace ownership. The adapter must implement `creation_cwd_verified()` and return the literal `True` only after verifying this capability; missing or false capability blocks all reconciliation. No live adapter has established this capability. A multi-call identity check in this core does not itself prevent a server swap inside a single adapter operation. API timeouts or missing/partial metadata must raise, never return an empty successful listing. All callers must share the same OS user, passwd home, filesystem and mount namespace, and use this core’s coordination protocol. The core takes a global flock in the fixed passwd-home directory `.herdr-ml-reconciliation-locks`, with no environment or call-site path override, before taking a per-state lock; state paths inside that directory are rejected. The adapter must return literal `True` from `coordination_verified()` only after establishing those shared-coordination properties; otherwise execution blocks. Cross-host, multiple-user, remote Herdr, private mount namespaces, older writers and differently mounted homes are unsupported and must block. The server, every writer and the lock directory are inside the trusted single-user boundary; a same-user process that unlinks or replaces the lock, or uses a different implementation, can bypass it. The lock directory must have owner-only permissions. State and lock files must reside on a filesystem providing local `flock`, atomic rename, and fsync semantics. The protected state directory is part of the single-user trust boundary.

The core persists and fsyncs unique ownership markers and an operation intent before creating a workspace or tab. On restart, it adopts exactly one matching object only if its server, marker and checkout match. A missing object after an uncertain operation is **BLOCKED**, including the crash-before-dispatch case: lack of a result does not prove a remote mutation failed. Operator investigation and an audited recovery procedure are required; deleting state or retrying blindly is unsafe. When local state is missing, any existing workspace (including an unmarked legacy workspace) with the same canonical checkout, or a managed workspace with the same label, blocks before new state or a new workspace is created. Any workspace with an unverifiable checkout blocks even when its displayed label differs: its inaccessible path may be an alias of the requested checkout. The error identifies the workspace ID and label for operator reconciliation; do not discard it or infer that it is unrelated. Matching duplicate markers, changed identity, missing workspace, changed checkout and reused IDs also block. It never deletes, renames, focuses, or starts commands. The core restores a missing managed tab with a new ID only after a complete authoritative inventory and with no unresolved intent. Existing unrelated tabs are left intact.

Mock-only verification:

```sh
python3 -m unittest discover -s tests -p 'test_herdr_reconcile.py' -v
```

The tests exercise simulated API failures and actual abrupt exit of a mock client after each remote mutation. They do not prove installed Herdr compatibility, permissions, server incarnation identity, actual pane layout, or recovery on a live server. A real adapter and an authorized, isolated Herdr session are mandatory before release. Reconciliation of panes/watchers beyond existence of a tab remains unimplemented.

Pending tab adoption and creation recheck the recorded workspace marker, checkout and ID before use; adoption also rechecks the parent after fetching the tab inventory. These checks prevent persisting an observed replacement in the mock model, but they are not atomic with remote server operations. A live adapter still needs a server-enforced incarnation/ownership condition, or must remain blocked.

The reconciler requires `atomic_parent_guard_verified()` and `parent_guard(...)` before creating any layout. The guard must prevent parent replacement, server/session incarnation changes, and competing tab changes from validation through tab inventory, mutation, and the local state file and parent directory fsync. A timeout-based lease that can expire during persistence is insufficient. Missing, false, or unsupported capabilities block. Test fakes return a simulated guard solely to exercise call ordering; their assertions do not establish a Herdr server capability. There is currently no live adapter, and whether installed Herdr can provide this atomic contract is unknown. Never set the capability to true based only on repeated client-side checks or a local process lock.

Adapter-reported workspace and tab creation cwd values must be absolute server paths. Relative paths and `~` are not expanded using the client's working directory or HOME. The operator-supplied checkout argument retains its documented local path expansion behavior.
