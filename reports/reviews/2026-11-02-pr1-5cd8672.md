## Blocking findings

### H1 — HIGH: duplicate workers execute the same run
- Location: `scripts/researchctl.py:231-250`, especially the read/check of status and subsequent atomic replacement.
- Root cause/scenario: `os.replace` makes each write atomic but does not make read/check/write a claim. Two workers can both read QUEUED, both write RUNNING, both launch the same job, truncate the same log files and race to overwrite result/status. A queue replay, ambiguous enqueue response or concurrent `_execute` causes duplicate GPU work and corrupted evidence. The completed-run test is sequential and cannot catch this.
- Reproduce: create a queued/submitted diagnostic record, synchronize two worker processes just after both read the status, then let both continue to execute an argv that appends its PID to a file. Both can append. No live queue required.
- Remediation: durable exclusive atomic claim per run with process ownership, recorded queue ID and safe recovery/fencing; make enqueue reconciliation idempotent and never blindly retry ambiguous submissions. Protect log and result ownership.
- Acceptance: deterministic multiprocess barrier test proves exactly one execution and one consistent result; crash at each claim/enqueue boundary and reconcile without duplicate execution or silent loss; repeat on real Pueue.

### H2 — HIGH: cancellation can leave GPU descendants alive
- Location: `scripts/researchctl.py:250-280` (`execute`, SIGTERM handler and `Popen`).
- Root cause/scenario: only the immediate child receives SIGTERM, with no process group/session ownership, escalation, descendant reaping or SIGINT handling. Launchers routinely spawn training workers; terminating the launcher can leave descendants running while the ledger reports INTERRUPTED and a serial queue advances to the next GPU job. SIGKILL, daemon failure or machine interruption also leave RUNNING with no reconciliation.
- Reproduce: submit a diagnostic command which spawns a long-lived child and exits on SIGTERM; terminate the ledger process and inspect the child and status. Use an isolated temporary checkout, CPU processes only.
- Remediation: supervise a dedicated process group or cgroup, propagate termination to the entire owned tree, wait and escalate safely, record verifiable process identity, and reconcile abandoned RUNNING jobs on restart before allowing another resource-consuming run. Do not kill unrelated reused PIDs.
- Acceptance: integration tests for SIGTERM, SIGINT, parent death, stubborn grandchildren and PID reuse demonstrate no orphaned process and truthful state; real queue cancellation and restart test proves no overlap.

### H3 — HIGH: official source and scientific provenance are not bound to execution
- Location: `scripts/researchctl.py:174-199, 243-266`; `gate_report` lines 90-121.
- Root cause/scenario: Git status is sampled before `Popen` in a mutable shared checkout; another agent can edit or switch it after that check, and argv can execute code outside the checkout. Dataset version and split hash are arbitrary strings, and gates only assert that local evidence files exist. Gate records are not bound to the submitted source, data, protocol or reviewer identity, and their content can change while queued. This is not proof of leakage prevention or scientific readiness, despite a structurally valid gate.
- Reproduce: create a clean Git checkout and structurally valid gates; submit official work, pause after the execution-time Git check and alter the checkout before the child reads it, or supply arbitrary split hash and placeholder evidence. The launcher does not verify actual dataset bytes or enforce a protected split.
- Remediation: execute an immutable materialized source snapshot or otherwise establish and verify immutable source identity through execution; bind reviewed gate and evidence digests, protocol and verified dataset/split manifest to the actual run, and make unverifiable provenance explicitly BLOCKED. Retain independent human scientific review, not a claim of automatic scientific certification.
- Acceptance: mutation/race and changed-evidence tests block or execute the original snapshot; mismatched data/split/gate digests fail closed; independent reviewers inspect actual provenance, OOD leakage analysis and protocol before governance readiness.

### H4 — HIGH: workspace bootstrap cannot reliably recover
- Location: `scripts/bootstrap-herdr.sh:39-48, 69-73`.
- Root cause/scenario: a live stored workspace ID causes an unconditional skip without checking identity, checkout, required tabs or watchers. IDs are server-scoped and may be reused in another session. Creation is only persisted after all tabs and watchers are created, so interruption/error after workspace creation leaves an unrecorded workspace and the next bootstrap creates another. Loss of server/session or changed project configuration makes stored IDs ambiguous.
- Reproduce: interrupt bootstrap after workspace create but before the final state-file move, then rerun in an isolated Herdr session; or remove a required tab and rerun with the saved ID. Code inspection predicts duplication or no repair, respectively. This was not executed here because this session is outside Herdr.
- Remediation: persist intent and returned workspace identity immediately, bind it to server/session and canonical project identity, discover and reconcile actual tabs/panes/watchers, and handle ambiguous create responses without blind retries. Fail visibly when ownership cannot be proven.
- Acceptance: isolated real-Herdr integration fault injection after every API mutation, session restart/ID collision, deleted tab and repeated bootstrap yields exactly one correct workspace per project or a safe explicit BLOCKED state.

- `shell=False` and argv list avoid shell interpolation for the actual child; queued wrapper uses `shlex.join`. This is an authorized arbitrary-code runner for one trusted user, not a sandbox. Logs/argv can contain secrets, as documentation warns. No Discord bot, authorization endpoint, or native plugins exist; their documentation identifies them as future work. Do not infer security readiness for absent integrations.
- The queue is cooperative; diagnostic and local runs can bypass it, and external CUDA jobs are outside its scope. Per-project config may name different groups. No kernel GPU lock, process isolation, memory admission, metric integration, dataset catalog, enforced OOD leakage checks, checkpoint/resume, backup/restore, or service supervisor is implemented. The roadmap identifies much of this as future work. Separate technical gate validation from real scientific judgment.
- No independent evidence here establishes model correctness, dataset quality, independent reviewer identity, statistical validity or real-world OOD performance.
